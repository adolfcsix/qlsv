# CẤU TRÚC BACKEND QLSV V06 — THIẾT KẾ ĐỀ XUẤT

**Nguồn đối chiếu:** `QLSV_FULLSTACK_UIUX_V05.zip` (07/11/2026). **Trạng thái:** tài liệu thiết kế cấu trúc; chưa phải backend V06 đã viết lại, chưa có bằng chứng kiểm thử V06.

**Mục đích:** Backend dễ đọc, dễ học, dễ giải thích trước giảng viên; chia đúng nghiệp vụ quản lý đại học; không làm mất chức năng và dữ liệu V05; không giữ file cũ trùng lặp sau khi chuyển đổi thành công.

## A. Hiện trạng được xác minh trong V05

- Node.js **HTTP thuần** với JavaScript ES Modules; **không dùng Express**.
- Cơ sở dữ liệu: **36 bảng SQL lõi** trong `qlsv-original.sql`, kèm **8 bảng mở rộng** trong `extensions.sql`. Driver MySQL (`mysql2`) hoặc SQLite (`node:sqlite`), chọn bằng môi trường.
- Có phiên đăng nhập qua cookie HttpOnly, CSRF, kiểm tra quyền, nhật ký thao tác, nhập/xem điểm, công bố kết quả, đăng ký lớp học phần, chatbot AI có kiểm soát quyền.
- Mã nghiệp vụ hiện còn tập trung trong `server.js`, `mutations.js`, `state.js`, `results.js`, `assistant.js`; `assistant.js` còn import logic ý định tra cứu từ thư mục `frontend/src`, chưa tách mã dùng chung đúng vị trí.
- API V05 sử dụng `/api/v1/state` (trả snapshot theo quyền) và `/api/v1/changes` (ghi nhiều loại thay đổi bằng một endpoint). Trong V06 nên chuyển dần sang API theo tài nguyên. **Không xóa endpoint cũ trước khi frontend và tests đã chuyển xong.**
- Phải tách **lớp hành chính** (`student_groups`) với **lớp học phần** (`classes`); **lần học** (`enrollments`) với **lần thi** (`exam_registrations`). Đây là hai cặp nghiệp vụ không được nhập làm một.

## E. Ví dụ giảng viên yêu cầu sửa “quản lý lớp theo khóa, ngành”

**Phần frontend:** `frontend/src/pages/academic/organization/student-groups.js` và thành phần lọc dùng chung.

**Đường đi xử lý backend:**

```text
Người dùng chọn khóa tuyển sinh / khoa / ngành
    ↓
GET /api/v1/student-groups?admissionYear=2024&majorId=...
    ↓
modules/organization/organization.routes.js
    ↓
modules/organization/organization.controller.js
    ↓
modules/organization/groups.service.js
    ↓
modules/organization/organization.repository.js
    ↓
MySQL: student_groups + curricula + majors + departments
    ↓
Trả {data: {items, pagination}} theo quyền người đăng nhập
```

Vì `student_groups` không lưu trực tiếp khoa/ngành/khóa một cách độc lập, cần JOIN qua `curricula` → `majors` → `departments` và trường năm tuyển sinh tương ứng. Bộ lọc phải phân trang, không tải tất cả sinh viên/lớp về trình duyệt để xử lý.

## G. Nguyên tắc cần bảo đảm khi viết code

1. **Dễ giải thích:** `routes` chọn địa chỉ, `controller` nhận/trả HTTP, `service` xử lý quy tắc, `repository` truy vấn SQL. Không viết HTML/CSS trong backend.
2. **Giữ đúng DB:** không xóa bảng lõi vì tên khó nhớ. Mọi thay đổi schema thực hiện qua migration có ghi chú.
3. **Quyền truy cập ở server:** 4 vai trò `ADMIN`, `ACADEMIC_STAFF`, `LECTURER`, `STUDENT`; không chỉ ẩn nút ở frontend. ADMIN quản trị hệ thống không mặc nhiên có toàn bộ hồ sơ học vụ.
4. **Không sao chép logic:** `students.service.js` chỉ xử lý hồ sơ; nghiệp vụ cấp lớp ở `organization`; nhập/công bố điểm ở `assessment`. Hàm dùng chung đặt trong `utils` hoặc `core`.
5. **Dữ liệu thật và demo phân biệt:** không đưa tài khoản/mật khẩu demo vào môi trường thật; key AI chỉ ở backend; không đưa SQL hay thông tin cá nhân vào log.
6. **Quy trình điểm có transaction:** tổng trọng số, điều kiện dự thi, tính điểm, công bố, nguồn điểm và audit phải nhất quán; khi lỗi rollback.
7. **Bảo mật:** cookie HttpOnly/SameSite, CSRF, băm mật khẩu, rate-limit, kiểm tra Origin cho thao tác ghi, tham số SQL ràng buộc, đầu vào hợp lệ.
8. **Hiệu năng:** lọc dữ liệu tại SQL, `LIMIT/OFFSET`, index phù hợp; tránh mô hình `/state` đọc hàng chục bảng trên mọi trang.
9. **Chatbot:** không được tự tạo hoặc thực thi SQL tuỳ ý; chỉ gọi tool tra cứu cho phép và kiểm tra quyền. Không dùng frontend để quyết định dữ liệu nào được trả.
10. **Không sót code cũ:** chuyển từng nghiệp vụ và test; sau đó loại bỏ `mutations.js`, `state.js`, `results.js`, `assistant.js` kiểu gom tất cả **chỉ khi** không còn nơi nào import và tests đã qua.
11. **Không chia quá vụn:** các file `*.controller.js` có thể bỏ qua với nghiệp vụ cực nhỏ khi controller chỉ một dòng; ưu tiên cấu trúc rõ ràng, không phải số lượng file.
12. **Một lệnh chạy từ gốc:** tiếp tục `npm run dev`, `npm run db:init`, `npm run db:seed`, `npm test`, `npm start` (sửa script tương ứng trong quá trình chuyển đổi, không tạo hai bộ cài độc lập).

## H. Bộ test cần có trước khi bảo vệ

- Đăng nhập/đăng xuất/đổi mật khẩu; phiên hết hạn; khóa tài khoản; CSRF.
- Phân quyền 4 vai trò: không chỉ ẩn UI, mà API không được trả hồ sơ/bảng điểm không có quyền.
- Tạo/sửa/xóa khi hợp lệ theo khóa → ngành → chương trình → lớp; chặn trùng mã và xóa có ràng buộc FK.
- Sinh viên đăng ký học phần: kiểm tra chỗ, lịch trùng, tiên quyết, rút học, lặp request, transaction.
- Nhập/công bố điểm: trọng số 100%, điểm hợp lệ, thi lại/thi bù, không sửa trực tiếp kết quả đã công bố.
- Chatbot: đếm lớp/sĩ số, tìm sinh viên, bảng điểm đúng quyền; prompt lạ không thể vượt quyền.
- Không mất dữ liệu khi chạy chuyển đổi SQLite/MySQL; kiểm thử migration và demo seed không lặp.
- Tính năng frontend gắn đúng endpoint V06; không còn request `/state` và `/changes` nếu đã loại bỏ.

## I. Trình tự tái cấu trúc hợp lý

**Giai đoạn 1:** Tách `core`, `config`, `middlewares`, giữ nguyên API đang chạy.

**Giai đoạn 2:** Tách `auth`, `accounts`, `organization`, `students`, `teaching` theo trình tự phụ thuộc; thêm API tài nguyên và kiểm thử.

**Giai đoạn 3:** Tách `enrollments`, `assessment`, `exams`, `requests`, `finance`, `reports`, `ai` mà không đổi quy tắc nghiệp vụ tùy tiện.

**Giai đoạn 4:** Chuyển frontend từng màn hình sang API mới, giữ tương thích khi chuyển và test lại 4 vai trò.

**Giai đoạn 5:** Dọn import, file cũ, routes cũ, dependencies không dùng; chạy test và viết README giải thích cho người bảo vệ.

---

**Chốt hướng:** Một repo JavaScript thuần; frontend và backend tách rõ; backend chia theo nghiệp vụ có lớp xử lý đủ để giải thích, không dùng kiến trúc cầu kỳ. Đây là bản cấu trúc hoàn chỉnh về phạm vi, **không đồng nghĩa tất cả tính năng đã được triển khai hoặc chạy ổn định**.
